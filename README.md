# The power of encapsulation and properties

An object has state - data it remembers over time.

The question is not *how do we store data?*
The question is:

> Who is allowed to change it?

If we expose raw fields publicly, any code can modify our internal state directly.
That makes the object fragile and unpredictable.

Encapsulation means:

* The object owns its state.
* Outside code cannot change that state arbitrarily.
* All access goes through controlled entry points.

In C#, properties are those controlled entry points.

They look simple from the outside:

```csharp
obj.MyProperty = 10;
var value = obj.MyProperty;
```

But inside the class, we decide what is allowed.

Validation protects the state when writing.
Formatting and derived values provide controlled views when reading.

That is the power of properties:
they separate **how something is used** from **how it is stored and protected**.

## Step 0: The default case

Most of the time, we start here:

```csharp
public int MyProperty { get; set; }
```

This is an auto-property.

It gives us:

* Public access
* Private storage (generated by the compiler)
* Clean syntax

It’s perfect when we don’t need special rules.

But what if we *do* need rules?

## Step 1: Make the control visible

If we want to show clearly that the property is just a doorway, we can expand it.

```csharp
private int _myProperty;

public int MyProperty
{
    get => GetMyProperty();
    set => SetMyProperty(value);
}

private int GetMyProperty()
{
    return _myProperty;
}

private void SetMyProperty(int value)
{
    _myProperty = value;
}
```

Nothing changed from the outside.

This still works:

```csharp
obj.MyProperty = 10;
```

But now the control is explicit.

* `_myProperty` is the storage.
* `MyProperty` is the doorway.
* `GetMyProperty` and `SetMyProperty` are the gatekeepers.

We’ve separated *interface* from *implementation*.

This is the same design principle you’ll see again and again in software.

## Step 2: Protect the state

Now the benefit becomes obvious.

If we want to enforce a rule, we don’t change how the property is used.
We change the logic behind it.

```csharp
private void SetMyProperty(int value)
{
    if (value < 0)
        throw new ArgumentException("MyProperty cannot be negative.");

    _myProperty = value;
}
```

From the outside:

```csharp
obj.MyProperty = -5;
```

Now fails.

The object refuses to enter an invalid state.

This is encapsulation in action.

The class is defending itself.

## Step 3: Separate state from presentation

State and presentation are not the same thing.

The stored value might be a number.
The user-facing view might be a formatted string.

Instead of mixing those concerns, we expose a derived view.

```csharp
public string MyPropertyDisplay => FormatMyProperty();

private string FormatMyProperty()
{
    return $"The value is: {MyProperty}";
}
```

Now:

* `MyProperty` represents the true internal state.
* `MyPropertyDisplay` represents a friendly, formatted view of that state.

We didn’t corrupt the stored value.
We added a controlled interpretation of it.

## What matters

At this point, the syntax is secondary.

What matters is this:

* A **field** is raw storage.
* A **property** is controlled access.
* `get` and `set` are not variables - they are executable logic.
* Encapsulation means the object protects its own correctness.

As systems grow, this idea becomes critical.

Without encapsulation, objects become bags of data.
With encapsulation, they become reliable units of behavior.

And that difference scales.
